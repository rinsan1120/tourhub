# TouringHub Decisions

更新日: 2026-10-03

設計判断と、その背景・注意点を記録します。

## 1. 静的サイト構成

決定:

- TouringHub はGitHub Pagesで公開できる静的サイトとして構成する。

理由:

- サーバーサイド処理なしで公開できる。
- 設定txtやGeoJSONをリポジトリ内に置いて読み込める。

注意:

- `fetch()` を使うため、ローカル確認はHTTPサーバー経由にする。
- サーバーサイドAPIや秘密情報を前提にしない。

## 2. Leaflet採用

決定:

- 地図表示は Leaflet 1.9.4 を使用する。

理由:

- 静的サイトで扱いやすい。
- OpenStreetMapタイルと組み合わせやすい。
- MarkerClusterなどのプラグインを利用できる。

注意:

- Leaflet本体やプラグインのCDN障害時は地図表示に影響する。
- 地図操作の独自タッチ制御はLeaflet標準操作と干渉し得る。

## 3. OpenStreetMapタイル利用

決定:

- ベース地図は `tile.openstreetmap.org` を使用する。

理由:

- APIキーなしで利用できる。
- Leafletと標準的に組み合わせられる。

注意:

- 利用ポリシーやアクセス負荷への配慮が必要。
- 大量アクセスが見込まれる場合は代替タイル提供元を検討する。

## 4. uMapデータ固定化

決定:

- uMap由来のデータを `umap_backup_map.umap` としてリポジトリ内で読み込む。

理由:

- GitHub Pages上で静的に読み込める。
- 外部uMap側の状態変化からサイト表示をある程度切り離せる。

注意:

- uMap側との同期手順は明文化が必要。
- `umap_backup_map.umap` はマスタ更新時にファイル全体を置き換える。
- 機能改修や性能改善のために内容、構造、書式を直接編集しない。
- アプリ側の要件は読み込み処理で吸収する。

## 5. 道の駅GeoJSON分離

決定:

- 道の駅は `P35-18_Roadside_Station.geojson` と `conf/michi-no-eki.js` で別読み込みにする。

理由:

- 国土数値情報由来データを独立して扱える。
- uMapデータとは別系統で更新できる。

注意:

- `道の駅` レイヤー名は他のレイヤー設定と重複し得る。
- 2018年データと更新ログに記載があり、鮮度には注意が必要。
- `P35-18_Roadside_Station.geojson` はマスタ更新時にファイル全体を置き換える。
- 機能改修や性能改善のために内容、構造、書式を直接編集しない。
- アプリ側の要件は読み込み処理で吸収する。

## 6. Open-Meteo採用

決定:

- 天気予報は Open-Meteo API を使用する。

理由:

- APIキーなしで利用できる。
- 複数地点の緯度経度をまとめて問い合わせられる。

注意:

- UI上で「海外データにつき精度が不安定」と注意喚起している。
- 出発前の詳細確認用にGoogle天気検索リンクを併設している。

## 7. Google Mapsリンク利用

決定:

- スポット表示、ルート検索、周辺検索はGoogle MapsのURLリンクで連携する。

理由:

- Google Maps APIキーなしで利用できる。
- ユーザーを外部地図アプリ/ブラウザへ誘導できる。

注意:

- Google Maps APIを直接導入する場合は課金・キー管理の検討が必要。
- URL仕様変更の影響は受ける可能性がある。

## 8. 設定txtによるデータ分離

決定:

- 周辺検索、リンク、天気地点、更新ログ、ドロワーは `conf/*.txt` で管理する。

理由:

- HTMLを直接編集せず、設定データだけ更新できる。
- AI作業時のデグレ範囲を狭められる。

注意:

- txt形式はパーサ実装に依存する。
- 形式変更時はJS側とドキュメントを同時に更新する。

## 9. モバイル独自ジェスチャ

決定:

- モバイルでは独自にダブルタップズームと片指ズームを実装する。

理由:

- スマホで片手操作しやすくするため。
- 2回目タップ保持から上下移動でズームできる。

注意:

- 長押しピン、Leaflet標準ジェスチャ、独自ジェスチャが干渉しやすい。
- 変更時は実機またはタッチ相当環境で確認する。

## 10. マスタ地図データの保護

決定:

- `umap_backup_map.umap` と `P35-18_Roadside_Station.geojson` を、置換更新される原本データとして扱う。
- 通常のアプリ改修では両ファイルを直接編集しない。
- 正規マスタによるファイル全体の置換だけを更新として認める。

理由:

- 両ファイルはマスタ更新のたびに置き換えられるため、手作業の変更が次回更新で失われる。
- アプリ固有の加工を原本へ加えると、更新作業とデータ整合性の維持が難しくなる。

注意:

- パフォーマンス改善や表示条件への対応はJavaScript側で行う。
- 元ファイルの手作業による分割、整形、項目追加を運用前提にしない。
- マスタ置換後は形式、参照プロパティ、レイヤー名、件数の互換性を確認する。

## 11. 今後記録すべき判断

- OpenStreetMapタイルの長期利用方針
- 高速道路ICデータの由来と更新手順
- uMap同期手順
- ドキュメント構成の正式化
- インラインJS/CSSを分離するかどうか

## 12. 気象庁雨雲レイヤー（2026-10-01）

ユーザーの実装依頼に従い、気象庁の公開Web配信用ナウキャストを独立したLeafletタイルレイヤーで表示します。APIキー・課金登録・追加ライブラリ・サーバー処理は不要です。2026-10-01に公式ページの配信設定、JSONとPNGの実レスポンス、CORSを確認しました。

- 実況: `https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N1.json`
- 予測: `https://www.jma.go.jp/bosai/jmatile/data/nowc/targetTimes_N2.json`
- タイル: `https://www.jma.go.jp/bosai/jmatile/data/nowc/{basetime}/none/{validtime}/surf/hrpns/{z}/{x}/{y}.png`
- 出典: https://www.jma.go.jp/bosai/nowc/

時刻はJSONから取得し、最新実況を時間選択の基準にします。5分キャッシュとON中だけの更新でアクセスを抑えます。代替は気象庁ページへのリンクですが、今回の目的は地図上での重ね合わせです。Web配信用URLや配信仕様は将来変更される可能性があり、その場合も雨雲だけを停止して地図利用を維持します。

## 13. OpenPOI場所検索（2026-10-03）

ユーザー指定のOpenPOI APIを施設名・地名の入力補完に採用しました。公式仕様 https://docs.openpoiapi.com/ と出典・ライセンス https://openpoiapi.com/attribution.html を確認し、ベースURL `https://api.openpoiapi.com`、`/v1/suggest`、認証不要・全オリジンCORS許可を確認しました。課金登録・APIキー・追加ライブラリ・サーバー処理は使用しません。提供形態・レート制限は将来変更される可能性があります。

検索パネルと既存出典フッターへ「検索データ：OpenPOI API」の公式出典リンクを追加します。個々の候補へライセンスを表示せず、検索結果の永続保存・再配布も実装しません。将来保存する場合の `licenses` / `attributions` 保持と再配布・加工公開条件の再確認はコードコメントにも残します。

代替は座標入力や外部地図への検索リンクですが、今回の場所検索にはOpenPOIを利用します。通信失敗・429・タイムアウトは検索のみのエラーとし、座標移動と他の地図機能を利用可能にします。

同日の追加修正で、周辺の誤った候補が優先される問題へのユーザー指示に従い、bbox・center・radiusを完全に除去して全国検索へ変更しました。入力補完は `/v1/suggest`、検索ボタンと入力欄Enterは `/v1/search` とします。2文字以下の全国suggestに施設が返らない場合も、位置条件で回避せず本検索で対応します。既存の地名応答のbbox/centerによる地図移動は維持します。
